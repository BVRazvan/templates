\chapter{Evaluation}
As this project approaches its end, it is a suitable moment to provide information regarding a few metrics. \\
The hardware used has the following specifications:
\begin{itemize}
    \item CPU: Intel(R) Core(TM) i5-7300HQ CPU @ 2.50GHz;
    \item Architecture: x86_64.
\end{itemize}
The following sections provide values related to the build phases of binary and native compatibility modes.
It is important to note that each figure presented here averages ten runs.
\section{Binary Compatibility Mode}
\subsection{Build Time}
\fig[scale=0.45]{./src/img/build_time_bincompat}{img:build_time_bincompat}{Build Time}
As the figure above suggests, the build process has been divided into three parts:
\begin{itemize}
    \item Build application refers to the part when the source files of the OpenArena server are compiled and linked together into an ELF file;
    \item Build file system measures the time to create the Docker image consisting of the OpenArena game code along with other necessary libraries;
    \item Build kernel counts the time taken to build the final unikernel image once the application and the file system are ready;
    \item Additionally, the build total is self-explanatory, summing up the values.    
\end{itemize}
\subsection{Build Size}
The relevant dimensions during the build phase are those of the kernel and file system. \\
Here, the file system is included in the kernel as the sizes are similar.\@
That said, the Unikraft libraries required to build the kernel are minimal, denoting the small attacking surface.

\fig[scale=0.45]{./src/img/build_size_bincompat}{img:build_size_bincompat}{Build Size}
\section{Native Compatibility Mode}
\subsection{Build Time}
In this mode, the build kernel part in native compatibility mode also includes compiling the application, providing better customizability. Unlike the other method, the file system is attached during runtime.
