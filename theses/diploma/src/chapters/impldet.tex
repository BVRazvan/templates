\section{Running the Server Locally}
The initial step completed is building and running the OpenArena server locally from source files in order to test its functionality and to get to understand
how the server works under the hood. \\ \\
Therefore, the archive with its engine is downloaded from GitHub\footnote{\url{https://github.com/OpenArena/engine}}, as it is an open-source project. \\
Besides this, there is another important archive that contains the main game code and assets (maps, models). It can be found on the official website\footnote{\url{https://openarena.ws/download.php}}. One important
detail is that it must be placed at a default file path: \textbf{.local/share/OpenArena/} unless another one is mentioned while creating the executable file. \\
Finally, the server application is compiled using the GNU make utility, offering multiple rules and targets for shaping the output to conform to specific needs.

\section{Diving into Engine Components}
The OpenArena is structured into several modular components, each responsible for a specific aspect of the game functionality.
This separation ensures modularity, adaptability, and scalability. \\ \\ 
The \textbf{server/} component contains the actual server-side game loop, client commands management, snapshot generation and networking code, having the following key roles:
\begin{itemize}
    \item Tracks and updates connected clients;
    \item Processes commands from clients;
    \item Sends game state snapshot to clients;
    \item Handles time steps and game simulation ticks.
\end{itemize} \\
The \textbf{game/} component contains the game logic virtual machine, having the following key roles:
\begin{itemize}
    \item Runs the actual game rules: player movement, combat, scoring;
    \item This is sandboxed and isolated from the main engine for modularity and safety;
\end{itemize} \\
The \textbf{botlib/} component contains the services for computer-controlled bots (routing, decision-making), having the following key role:
\begin{itemize}
    \item Provides support for bot players.
\end{itemize} \\
The \textbf{qcommon/} component has code shared by both the client and server side, like system handling, memory management and command parsing, having the following key roles:
\begin{itemize}
    \item Acts as the glue between engine components;
    \item Includes core logic for configuration system.
\end{itemize} \\
The \textbf{sys/} component abstracts OS-level functionality like timing, threading, file I/O and networking, having the following key roles:
\begin{itemize}
    \item Provides a portable implementation of low-level tasks;
    \item Required for the server to interact with OS.
\end{itemize} \\
The \textbf{asm/} component offers performance-critical assembly routines, including vector math, having the following key role:
\begin{itemize}
    \item Used where performance matters
\end{itemize} \\
The \textbf{null/} component exposes dummy implementations of rendering-related functions, having the following key role:
\begin{itemize}
    \item Allows server builds to run without full graphics initialization.
\end{itemize} \\
The \textbf{zlib/} component contains standard compression utility, having the following key roles:
\begin{itemize}
    \item Used for compressing messages, files, or game states;
    \item Provides excellent bandwidth and storage efficiency. \\
\end{itemize}

\section{Running in Binary Compatibility Mode}
Now, Unikraft comes into play. Thanks to its design, POSIX and Linux compatible, it is possible to run unmodified Linux ELF files on top of Unikraft, using the ELF Loader\footnote{\url{https://github.com/unikraft/app-elfloader}}. \\
This approach boils down to two files: a Dockerfile and a Kraftfile. These are used by kraft\footnote{\url{https://unikraft.org/docs/cli}}, a CLI tool
provided by Unikraft. Therefore, the process of creating an unikernel simplifies drastically.

\subsection{Dockerfile}
The \textbf{Dockerfile}\footnote{\url{https://docs.docker.com/reference/dockerfile/}} creates the Docker image whose content represents the file system. \\
It follows the philosophy of unikernels, containing only necessary and sufficient dependencies to run the application.
Thus, the Docker image has an OpenArena server ELF file, compiled from source files, and the OpenArena game code. \\ \\
To satisfy runtime dependencies identified by the \textit{ldd}\footnote{\url{https://man7.org/linux/man-pages/man1/ldd.1.html}} utility, the C library (libc) and the math library (libm) are included too.
The image also exposes UDP port 27960, which is the default OpenArena game port, allowing clients to connect and play over the network.
\fig[scale=0.785]{./src/img/dockerfile.drawio.pdf}{img:Dockerfile}{Dockerfile}
\subsection{Kraftfile}
The \textbf{Kraftfile}\footnote{\url{https://unikraft.org/docs/cli/reference/kraftfile/v0.6}} is the real coordinator. It configures the unikernel by incorporating individual components from the Unikraft environment
and beyond it. Thus, it is important to understand the role of the modules, a short yet expanded description of several of them is mandatory.
\begin{itemize}
    \item The \textbf{libukboot} library takes care of bootstrapping, calling various constructors, and lastly, the main function of the application;
    \item The \textbf{libvfscore} library provides a generic interface of system calls related to file system management; 
    \item The \textbf{libdevfs} library brings a special file system for registering, and inspecting devices;
    \item The \textbf{libramfs} library presents a RAM file system;
    \item The \textbf{libukvmem} library adds support for virtual memory, automatically implying paging and interrupt routines mechanisms;
    \item The \textbf{libukalloc} library is an abstraction for memory allocators;
    \item The \textbf{libukallocbbudy} library is a memory allocator, based on the buddy\footnote{\url{https://www.kernel.org/doc/gorman/html/understand/understand009.html}} technique. This approach minimizes fragmentation while supporting dynamic memory allocation with a balance between speed and efficiency.
    \item The \textbf{libposix-*} libraries offer compatibility with POSIX standards, providing essential abstractions for processes, sockets, and file descriptors. They also include support for functionality like event polling, memory mapping, and interprocess communication;
    \item The \textbf{libuksched, libukschedcoop} libraries imply scheduling capabilities. Specifically, libukschedcoop implements a cooperative scheduler where tasks voluntarily yield control, making it suitable for applications with predictable workloads and minimal concurrency complexity;
    \item The \textbf{libsyscall_shim}\footnote{\url{https://unikraft.org/docs/internals/syscall-shim}} library provides Linux-style mappings of system call numbers to actual system call handler functions; 
    \item The \textbf{libuknetdev} library is an interface for network drivers;
    \item The \textbf{liblwip} library is the Unikraft port of lwIP\footnote{\url{https://github.com/lwip-tcpip/lwip}}, a small independent implementation of the TCP/IP protocol suite. It supports essential networking protocols, including TCP, UDP, DHCP;
    \item The \textbf{libelf} library is the Unikraft port of libelf from the official ELF Tool Chain 0.7.1\footnote{\url{https://sourceforge.net/projects/elftoolchain/}}. It enables parsing, reading, and manipulation of ELF binaries;
    \item The \textbf{app-elfloader}\footnote{\url{https://github.com/unikraft/app-elfloader}} library extends Unikraft capabilities by allowing it to load and execute unmodified Linux ELF binaries. This makes it easier to run existing applications within a unikernel environment without rewriting them;
    \item The \textbf{Dockerfile} describes the docker image, whose content is used as a file system.
\end{itemize}
\fig[scale=1]{./src/img/kraftfile.drawio.pdf}{img:Kraftfile}{Kraftfile}
\subsection{Build Phase}
Having these two files set, the build phase can start. For \textbf{building} the unikernel on x86 with KVM/QEMU, the following command is used:
\\
\lstset{caption=Build the OpenArena server, language=C}
\begin{lstlisting}
kraft build --no-cache --no-update --plat qemu --arch x86_64 .
\end{lstlisting}
\\
Internally, two things happen. First, a Docker image is generated based on the Dockerfile. Its content is then converted into a CPIO archive to be integrated into the binary file. \\ \\
Subsequently, the unikernel is constructed by downloading and individually compiling the specified libraries, and assembling them into the final unikernel image.
\fig[scale=0.9]{./src/img/build_phase.drawio.pdf}{img:build_phase}{Build Phase}
\subsection{Run Phase}
Once the build is finished, the OpenArena server is ready to be launched. For \textbf{running} the unikernel on x86 with KVM/QEMU, the following command is used:
\\
\lstset{caption=Run the OpenArena server, language=C}
\begin{lstlisting}
kraft run --rm -M 2048M -p 27960:27960/udp --plat qemu --arch x86_64 .
\end{lstlisting}
\\
During the running phase, the kraft tool leverages QEMU to virtualize the environment produced during the build stage.
Within this virtualized runtime, the ELF Loader has a significant job: it is responsible for loading and preparing the OpenArena server for execution. This preparatory work is executed following the termination of the Unikraft booting procedure. \\ \\
The ELF Loader manipulates the file system using usual I/O operations and the libelf API.
The libelf library is used not only to open and read the ELF binary file but also to examine the file headers, which involve several other processes such as segment mapping which is done using mmap and set relevant memory protection flags. \\ \\
This information will now all be contained in a proper context structure that captures every piece of mandatory runtime information. After the context is added, the ELF Loader instantiates a thread that is responsible for server execution. \\ \\
Finally, the initialized thread will be run which in turn will commence the server startup functions.
\fig[scale=1.05]{./src/img/run_phase.drawio.pdf}{img:run_phase}{ELF Loader during Run Phase}
\section{Running in Native Compatibility Mode}
Running in native compatibility mode involves working directly with low-level tools and principles, such as GNU Make, GCC\footnote{\url{https://gcc.gnu.org/}}, Kconfig, and QEMU.
Unlike the prior method, where the ELF Loader performed application integration into the unikernel, now it becomes a developer responsibility. The developer is responsible for including the source files they want to incorporate into the final unikernel image. \\ \\
This approach offers high precision control over the application turning into a unikernel and the kernel libraries that come with it.
From the files engaged and finishing with the compilation flags and Makefile rules, it is up to the user to craft the most convenient binary image for its particular usage. \\ \\
Unfortunately, it is complex to handle because it is a thorough routine. The developer has to possess a great understanding of the build process and compilation options of the target application, in addition to details about the architecture, build system, and libraries of Unikraft.
Therefore, solid knowledge goes hand in hand with best performance when a functional and lightweight unikernel is desired. \\ \\ 
This time, the native compatibility mode revolves around three files: Makefile, Makefile.uk, and Config.uk.
\subsection{Makefile}
The Makefile is used to specify the path of the Unikraft repository and other variables, such as external libraries that the OpenArena server needs to use:
\begin{itemize}
    \item libmusl presents the Unikraft port of musl\footnote{\url{https://musl.libc.org/}}, a C standard library built on the Linux system call API.
    Its usage for the server is obvious, providing support for memory management, string manipulations, and so on;
    \item liblwip is the Unikraft port of the lwIP network stack, which was also used in the previous chapter.
    As the application has a client-server design and the communication is done over the network, importing it is obligatory;
    \item libzlib integrates the Unikraft port of the zlib\footnote{\url{https://github.com/madler/zlib}}, a general-purpose data compression library.
    This allows the server to load the game code dynamically at runtime.
\end{itemize}
However, considering its rules, one can notice that this is a wrapper around the Unikraft core Makefile.
\\
\lstset{basicstyle=\small\ttfamily, caption=Makefile, language=make}
\begin{lstlisting}
UK_ROOT ?= $(PWD)/workdir/unikraft
UK_BUILD ?= $(PWD)/workdir/build
UK_APP ?= $(PWD)
LIBS_BASE = $(PWD)/workdir/libs
UK_LIBS ?= $(LIBS_BASE)/musl:$(LIBS_BASE)/lwip:$(LIBS_BASE)/zlib

.PHONY: all

all:
	@$(MAKE) -C $(UK_ROOT) L=$(UK_LIBS) A=$(UK_APP) O=$(UK_BUILD)

$(MAKECMDGOALS):
	@$(MAKE) -C $(UK_ROOT) L=$(UK_LIBS) A=$(UK_APP) O=$(UK_BUILD) $(MAKECMDGOALS)
\end{lstlisting}
\\
\subsection{Makefile.uk}
The Makefile.uk defines the source files required to build the OpenArena server.
Therefore, it explicitly lists the paths to the source code, included directories as well as compiler flags using a well-documented syntax:
\begin{itemize}
    \item \textit{APP[NAME]_BASE} variable keeps the path to the source files directory;
    \item \textit{APP[NAME]_CINCLUDES-y} variable brings together included directories for C files;
    \item \textit{APP[NAME]_SRCS-y} variable includes source files;
    \item \textit{APP[NAME]_[FILENAME]_FLAGS-y} variable instructs the compiler which flags to use for a given file.
\end{itemize}
This contrasts with binary compatibility mode, where the app-elfloader automatically extracts such information from the server binary during runtime. \\ \\
Recalling the components of the OpenArena engine described at the beginning of the chapter, these are now specified in this file to provide the same functionality.
\\
\lstset{basicstyle=\small\ttfamily, caption=Part of Makefile.uk, language=make, showstringspaces=false, keepspaces=true}
\begin{lstlisting}
$(eval $(call addlib,appopenarena))

CFLAGS_OA = -std=gnu11 -Wall -fno-strict-aliasing -Wimplicit -Wstrict-prototypes -pipe -DSTANDALONE -DPRODUCT_VERSION=\"3\" -Wformat=2 -Wno-format-zero-length -Wformat-security -Wno-format-nonliteral -Wstrict-aliasing=2 -Wmissing-format-attribute -Wdisabled-optimization -Werror-implicit-function-declaration -MMD -D__linux__

OPTIMIZE_OA = -DNDEBUG -O3 -fomit-frame-pointer -funroll-loops -ffast-math -flto

SERVER_CFLAGS_OA = -DUSE_VOIP

APPOPENARENA_CINCLUDES-y += -I$(APPOPENARENA_BASE)/code/asm
..
APPOPENARENA_CINCLUDES-y += -I$(APPOPENARENA_BASE)/code/sys

APPOPENARENA_SRCS-y += $(APPOPENARENA_BASE)/code/server/sv_bot.c
APPOPENARENA_SV_BOT_FLAGS-y += -DDEDICATED $(CFLAGS_OA) $(SERVER_CFLAGS_OA) $(OPTIMIZE_OA)

..
\end{lstlisting}
\\
\subsection{Config.uk}
The Config.uk is a Kconfig-like configuration file contributing entries to the Unikraft Kconfig-base menu system.
It allows users to enable or disable features via tools such as \textit{menuconfig} and to set parameters and dependencies
between components. Each entry represents a kernel module or library that provides specific mechanisms the unikernel requires. \\ \\
In the case of the OpenArena server, these entries correspond to the necessary libraries that enable successful booting and runtime behavior.
This file is included during the build process to render the configuration menu and to generate and parse the \textit{.config} file which holds the
selected settings. \\ \\
The libraries mentioned here are similar to those in the Kraftfile when using binary compatibility mode. In that mode, Kraftfile also allows the definition
of Kconfig options.
\\
\lstset{basicstyle=\small\ttfamily, caption=Config.uk, language=C, showstringspaces=false, keepspaces=true}
\begin{lstlisting}
# Config OpenArena Server application

config APPOPENARENA
bool "A server for OpenArena, a community-produced deathmatch FPS based of GPL idTech3 technology"
default y
    select LIBPOSIX_EVENTFD
    select LIBPOSIX_USER
    select LIBUKVMEM
    select LIBPOSIX_MMAP
    select LIBVFSCORE
    select LIBVFSCORE_AUTOMOUNT_UP
    select LIBUKCPIO
    select LIBDEVFS
    select LIBDEVFS_AUTOMOUNT
    select LIBDEVFS_DEVSTDOUT
    select LIBMUSL
    select LIBUKNETDEV_EINFO_LIBPARAM
    select LIBLWIP
    select LWIP_TCP_KEEPALIVE
    select LWIP_THREADS
    select LWIP_IPV6
    select LWIP_DHCP
    select LIBZLIB
\end{lstlisting}
\\
\subsection{Build Phase}
The build phase can almost begin with the main configuration files correctly set up.
One more thing to do is to select the appropriate target architecture and platform, in this case, x86 and KVM/QEMU. It can be done using the \textit{make menuconfig} command introduced earlier. \\ \\
Another step is packaging the game code into a CPIO archive, which serves as the file system for the unikernel.
The server will load this archive resources like maps, characters, and animations at runtime. \\ \\
Finally, build process is kicked off using the \textit{make} command, which activates the Makefile. 
As mentioned, this file triggers the actual workflow of the root Unikraft Makefile. \\ \\
During build stage\footnote{\url{https://unikraft.org/docs/internals/build-process}}, all the Makefile.uk files (from the Unikraft core and external libraries) are evaluated. The selected files are compiled and linked to form the unikernel image.
\\
\fig[scale=0.7]{./src/img/build_local_native.drawio.pdf}{img:build_local_native}{Build Phase}
\\  
\subsection{Run Phase}
In the runtime phase, the focus is entirely placed on the OpenArena server.
This results from the extra effort invested in the build stage where source files are incorporated individually, along with other various configurations. \\ \\
For launching the server, the following command is invoked:
\\
\lstset{basicstyle=\small\ttfamily, caption=Run Command, language=C, showstringspaces=false, keepspaces=true}
\begin{lstlisting}
sudo qemu-system-x86_64 \
    -nographic \
    -m 2048M \
    -cpu max \
    -kernel workdir/build/openarena_qemu-x86_64 \
    -initrd initrd.cpio
    -append "netdev.ip=172.44.0.2/24:172.44.0.1::: vfs.fstab=[\"initrd0:/:extract::ramfs=1:\"] -- +set dedicated 1 +map oa_dm5" \
    -netdev bridge,id=en0,br=virbr0 \
    -device virtio-net-pci,netdev=en0 \
\end{lstlisting}
\\
Although the command may seem complex initially, it can be easily understood by dividing it into smaller parts:
\begin{itemize}
    \item The first directive runs the command with root privileges, launching QEMU with x86_64 architecture emulation;
    \item The second directive turns off display video output, redirecting console I/O to the terminal;
    \item The third directive sets RAM size;
    \item The fourth directive tells QEMU to emulate a CPU with the maximally supported features of the host CPU, improving performance;
    \item The fifth directive specifies the kernel previously built;
    \item The sixth directive loads the archived game code as the initial RAM disk;
    \item The seventh directive appends command-line arguments serving multiple purposes. Firstly, it provides an IP Address and a default gateway to the VM. Secondly, it mounts the content
    of the CPIO archive;
    \item The eighth directive sets up networking bridging, connecting the virtual machine to an existing host bridge network (virbr0), allowing it to appear on the same LAN (Local Area Network) as the host while
    it also assigns an identifier (en0) to this network backend;
    \item The ninth directive adds a VirtIO network device backed by the same device (en0).
\end{itemize}
\\
Following the boot sequence of the Unikraft unikernel, control is directly handed off to the OpenArena server.
This represents the main change from the earlier method, where the ELF Loader application was first scheduled to execute, adding overhead.

\section{Packaging into a Unikraft Library}
One selling point of Unikraft is its focus on modularity. The entire ecosystem is represented by small standalone libraries with
well-defined roles. Therefore, one can build custom unikernels in a drag-and-drop manner as the implementations under the hood
glue the components like building blocks. \\ \\
A natural step forward is creating one such external library for the OpenArena server. Subsequently, a clean separation of concerns can be achieved
by turning the server into a Unikraft-compatible library. The application logic remains independent, while
the library enables easy use, configurability, and integration into unikernels. \\ \\
The core elements are defined across four files: Config.uk, Library.uk, Makefile.uk and, main.c, detailed below.
\subsection{Library.uk}
The Library.uk serves as a metadata descriptor for the library.
It provides essential information such as the library name, version, license, etc.
\\
\lstset{basicstyle=\small\ttfamily, caption=Library.uk, language=C, showstringspaces=false, keepspaces=true}
\begin{lstlisting}
name        := "OpenArena Server"
description := "A server for OpenArena, a community-produced deathmatch FPS based of GPL idTech3 technology."
homepage    := "https://openarena.ws/"
version     := 0.8.8 6f768215fc27355a90a3fd35b4078fa4d88ac60a79a665de7d4eb8aaf267a5c5 https://github.com/OpenArena/engine/archive/refs/heads/master.zip
license     := "GPL-2.0"
\end{lstlisting}
\\
\subsection{Config.uk}
The Config.uk is mainly similar to the one used in the native mode setup, with a few adjustments.
For example, libraries related to the file system have been opted out, reflecting the user preference. \\ \\
On a different note, this file emphasizes the modular direction of Unikraft. It introduces multiple variables that allow users to turn on or off individual components of the
OpenArena engine. These are enabled by default, ensuring completeness but providing flexibility for custom builds.
\\
\lstset{basicstyle=\small\ttfamily, caption= Part of Config.uk, language=C, showstringspaces=false, keepspaces=true}
\begin{lstlisting}
menuconfig LIBOPENARENA
    bool "LIBOPENARENA - a server for OpenArena, a community-produced deathmatch FPS based of GPL idTech3 technology"
    default n
    select LIBPOSIX_EVENTFD
    ..
    select LIBZLIB

if LIBOPENARENA

config LIBOPENARENA_MAIN_FUNCTION
    bool "Provide main function"
    default n

config LIBOPENARENA_ASM
    bool "Provide assembly code for optimized math calculations"
    default y

config LIBOPENARENA_BOTLIB
    bool "Provide code supporting bot players actions"
    default y

config LIBOPENARENA_GAME
    bool "Provide code for ingame logic"
    default y

config LIBOPENARENA_NULL
    bool "Provide code for dummy implementations of rendering-related functions"
    default y

config LIBOPENARENA_QCOMMON
    bool "Provide common code for server and client"
    default y

config LIBOPENARENA_SERVER
    bool "Provide code for the game loop, frames generation and networking communication"
    default y

config LIBOPENARENA_SYS
    bool "Provide code for OS-level interaction"
    default y

endif

\end{lstlisting}
\\
\subsection{Makefile.uk}
The Makefile.uk differs from the one in the native compatibility mode in its integration with the Kconfig system.
Rather than explicitly listing all source files, it relies on the configuration options selected through the Kconfig menu. \\ \\
As a result, only the components of the OpenArena engine that have been enabled in the configuration are included in the build.
\\
\lstset{basicstyle=\small\ttfamily, caption= Part of Makefile.uk, language=make, showstringspaces=false, keepspaces=true}
\begin{lstlisting}
$(eval $(call addlib_s,LIBOPENARENA,$(CONFIG_LIBOPENARENA)))

LIBOPENARENA_VERSION = 0.8.8
LIBOPENARENA_BASENAME = engine-master
LIBOPENARENA_URL = https://github.com/OpenArena/engine/archive/refs/heads/master.zip
$(eval $(call fetch,LIBOPENARENA,$(LIBOPENARENA_URL)))

LIBOPENARENA_SRC = $(LIBOPENARENA_ORIGIN)/$(LIBOPENARENA_BASENAME)/code

LIBOPENARENA_SRCS-$(CONFIG_LIBOPENARENA_MAIN_FUNCTION) += $(LIBOPENARENA_BASE)/main.c

LIBOPENARENA_CINCLUDES-$(CONFIG_LIBOPENARENA_ASM) += -I$(LIBOPENARENA_SRC)/asm
..
LIBOPENARENA_CINCLUDES-$(CONFIG_LIBOPENARENA_SYS) += -I$(LIBOPENARENA_SRC)/sys

LIBOPENARENA_SYS_MAIN_FLAGS-y += -Dmain=OPENARENA_main

LIBOPENARENA_SRCS-$(CONFIG_LIBOPENARENA_SERVER) += $(LIBOPENARENA_SRC)/server/sv_bot.c
LIBOPENARENA_SV_BOT_FLAGS-$(CONFIG_LIBOPENARENA_SERVER) += -DDEDICATED $(CFLAGS_OA) $(SERVER_CFLAGS_OA) $(OPTIMIZE_OA)

..
\end{lstlisting}
\\
\subsection{main.c}
The main.c file provides an entry point for the application. Here, additional initialization routines can be inserted, before starting the OpenArena server. \\ \\
However, its inclusion in the build process depends on a configuration variable set by the user.
\\
\lstset{basicstyle=\small\ttfamily, caption= main.c, language=C, showstringspaces=false, keepspaces=true}
\begin{lstlisting}
extern int OPENARENA_main(int argc, char* argv[]);

int main(int argc, char *argv[])
{
    return OPENARENA_main(argc, argv);
}
\end{lstlisting}
\\
\section{Running from the External Unikraft Library}
With the addition of previously detailed files, the OpenArena server can now made into a Unikraft library.
These provide the necessary configuration and initialization logic to transform the engine into a functional unikernel component.
\fig[scale=0.5]{./src/img/external_library.drawio.pdf}{img:exteral_library}{OpenArena Server as External Unikraft Library}
\subsection{Build Phase}
The existence of the external library leads to a simpler build phase.
Here, lib-openarena library includes the required source files and application-related configurations, so there is no need for the Makefile.uk used in the native compatibility mode. \\
The Config.uk includes file system libraries, reflecting the specific variant chosen by the user.
The top-level Makefile specifies the same external libraries used previously and includes the newly created
lib-openarena. \\
As in the last setup, the game code must once again be packaged into a CPIO archive, which justifies the inclusion
of the file system component.
\fig[scale=0.5]{./src/img/build_local_external.drawio.pdf}{img:build_local_external}{Build Phase}
\\
\subsection{Run Phase}
The run phase is quite similar to the native compatibility mode. \\ \\
The only difference is made by the main.c file, whose main function is called after the boot sequence. In the absence of other initialization work done,
the server starts immediately. This design separates the preliminary setup from the game logic.
\fig[scale=0.65]{./src/img/run_local_external.drawio.pdf}{img:run_local_external}{Run Phase}
